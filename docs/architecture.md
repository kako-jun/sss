# アーキテクチャ

sss（Smart Slide Show）の内部構造を実装に即してまとめたドキュメントです。新機能の追加・既存機能の修正時に、どのレイヤ・どのモジュールを触ればよいかの地図として使います。

## 1. 概要

sss は、10万枚規模の写真・動画コレクションを **完全平等ランダム** で再生するデスクトップ向けスライドショーアプリです。「ランダム表示なのに同じ写真ばかり出る」問題を、シャッフルベースのプレイリストで解決し、すべての写真に均等な出番を与えます。

### 技術スタック

| 層                 | 技術                                                   |
| ------------------ | ------------------------------------------------------ |
| デスクトップシェル | Tauri v2                                               |
| フロントエンド     | React 19 + TypeScript + Vite                           |
| UI                 | Tailwind CSS / framer-motion / lucide-react / uPlot    |
| バックエンド       | Rust                                                   |
| 永続化             | SQLite（rusqlite）                                     |
| 画像処理           | image / kamadak-exif                                   |
| ファイル走査       | walkdir + rayon（並列メタデータ取得）+ globset（除外） |

## 2. レイヤ構成

フロントエンド（React）とバックエンド（Rust）は Tauri の IPC（`invoke` / イベント）を介して通信します。フロントエンドはファイルシステムや DB に直接触らず、すべての永続化・走査・画像処理はバックエンドが担います。

```
┌──────────────────────────────────────────────────────────┐
│  React フロントエンド（WebView）                          │
│    App.tsx ─ Slideshow / OverlayUI / Settings/*           │
│    hooks（useSlideshow / useMouseIdle）                    │
│    lib/tauri.ts（IPC ラッパ）                              │
└───────────────┬──────────────────────────────────────────┘
                │  Tauri IPC
                │   ・invoke(command, args)  … 要求/応答
                │   ・listen("scan-progress") … 進捗イベント
                │   ・convertFileSrc(path)    … ローカル画像の表示
┌───────────────┴──────────────────────────────────────────┐
│  Rust バックエンド                                         │
│    commands/*（IPC コマンドの入口）                       │
│    AppState（db / playlist / directory_path / cache_dir /  │
│              cache_worker）                                │
│    playlist / scanner / image_processor / cache_worker /   │
│    ignore / database                                       │
└───────────────┬──────────────────────────────────────────┘
                │
        ┌───────┴────────┐
        ▼                ▼
   SQLite（sss.db）   ファイルシステム
   ・メタデータ        ・写真/動画の原本（読み取り）
   ・表示統計          ・キャッシュ（4K縮小/WebView非対応形式変換、サイズ上限付きLRU）
   ・除外ルール        ・ピック先フォルダ（sss-picked）
   ・設定/スキャン履歴
```

各層の責務:

- **React フロントエンド**: 表示・ユーザー操作・タイマー進行のみを持つ。状態（現在の画像・再生中フラグ・進捗）は React 側に、永続データはすべてバックエンド側に置く。
- **Tauri IPC**: フロントとバックの唯一の境界。コマンド呼び出し（`invoke`）と、長時間処理の進捗通知（`scan-progress` イベント）の2系統。
- **Rust バックエンド**: ファイル走査・差分検出・画像最適化・統計・設定永続化を担う。アプリ全体の可変状態は `AppState`（`Mutex` で保護）に集約する。画像最適化キャッシュの生成は単一ワーカースレッド（`cache_worker.rs`）が直列に行う。
- **SQLite / ファイルシステム**: メタデータ・統計・設定は SQLite に、画像原本は読み取り専用、加工済み画像は起動時に退避→バックグラウンド削除でクリアする・サイズ上限（既定2GB、直近提供分は除外）を超えたら古いものから削除するキャッシュに置く。

## 5. データフロー

### ① ディレクトリスキャン（差分）

`perform_scan`（`commands/scan.rs`。Tauri非依存の純粋関数、`select_and_scan`/`rescan_last_directory` コマンドは共通の `scan_chosen_directory` 経由でこれを呼ぶ薄いシェル）が次の順に行う（#61 M2/S1 で「物理的な事実」と「プレイリストに含めるべき集合」を明確に2段階に分離した）。`scan_chosen_directory` は `ScanGuard`（`AppState::scan_in_progress`）で二重実行を防ぎ、実行中に2本目が呼ばれた場合は即座に `Err` を返す（#61レビュー nit）:

1. （初回のみ）`.sssignore` の DB 移行を試みる。
2. DB から前回のファイルメタデータを読む。`Database::get_file_metadata_under(directory)` で**今回スキャンするディレクトリ配下のパスだけ**に限定する（#63）。以前は `get_all_file_metadata`（DB全件）を使っており、フォルダA→Bへ切り替えてスキャンした瞬間、Bのスキャン結果には現れないAのファイルが「今回の生スキャンに存在しない」と誤判定されて確定削除されてしまう事故があった。`get_file_metadata_under` は区切り文字境界での前方一致（`LIKE ... ESCAPE`）で判定するため、`/p/foo` を対象にしても `/p/foobar` を巻き込まない。A→B→Aと切り替えても各ディレクトリの `file_metadata`/`image_stats` は保持される（回帰テスト: `tests/playlist_persistence_e2e.rs::switching_a_to_b_and_back_to_a_preserves_a_file_metadata_and_display_stats`）。
3. **生スキャン**: `scanner.rs` が `walkdir` で対象拡張子（画像 8種 / 動画 4種）のファイルを**除外ルールを一切適用せず**集める。`rayon` で並列に `mtime`・`size` を取得し、100件ごとに進捗を `scan-progress` イベントで通知する。`walkdir` の読み取りエラー（権限拒否等）とファイル単位の `mtime`/メタデータ取得エラー（1970-01-01より前のmtimeで `duration_since` が失敗するケースを含む）は、以前は黙って結果から除外していたが、#63で `ScanError { path, message }` として収集するように変えた。エラーが起きても進捗カウントは必ず進め（`total` に届かず最終進捗イベントが発火しないという不具合を修正）、エラーが起きたパス（ディレクトリの場合はその配下も）は次のステップで「不明」として扱う。
4. 前回メタデータと突き合わせ、**新規**（パスなし）・**変更**（`mtime` 不一致）・**削除**（前回にあって今回ない）を判定する（変更は新規扱い）。この判定は除外ルールと無関係な「物理的な事実」だけを基準にする。今回エラーになったパス（またはその配下）は「不明」（`unknown_files`）に分類し、確定削除とは区別する（§6(b)の「確定削除と『不明』の区別」参照、#63で対象をディレクトリ系除外の枝刈りだけでなくエラーにも拡張）。
5. 結果を DB へ反映する。`Database::apply_file_metadata_changes(upserts, deleted_paths)` が**新規/変更分のみ**のupsertと確定削除分の削除を**1トランザクション・`prepare_cached`**でまとめて行う（#63）。以前は生スキャンで見つかった全ファイル（大半は「変更なし」）を毎回1件ずつ`upsert_file_metadata`していたが、10万件規模では大半が無駄なI/O・ロック保持時間の伸長になっていた。ロック保持時間は`perform_scan`内で計測し、100msを超えたら`eprintln!`で記録する。upsert は `ON CONFLICT DO UPDATE` で `modified_time`/`file_size` のみ更新し `added_at` を保持する。「不明」扱いのファイルはここに含めず、`file_metadata`/`image_stats`/`exif_cache` のいずれも保持したままにする。この後スキャン履歴記録＋100件超の刈り込みを行う。
6. DB から除外ルール（`pattern`+`rule_type`）を読む（このルール一覧は `walkdir` の枝刈り・撮影日ルールの有無判定に使う。ステップ2と同じタイミングでDBロックを取って読む）。撮影日ルールが1件以上あれば、`exif_cache` に未取得/古い（ファイルのmtimeが食い違う）候補だけ `rayon` で並列にEXIFを読み直し、結果を `exif_cache` へバッチ書き込みする（無ければ一切EXIFを読まない）。
7. **除外ルールを読み直し、`IgnoreFilter::from_rules_with_captured_dates` で「含めるべき集合」を計算する**（#61レビュー S-1 → `#62レビュー2巡目 N-S3`(must)で強化）。ステップ2・6は生スキャン・EXIF並列読みの**前**に短時間ロックで読んだものであり、10万件規模ではその後の処理に数秒〜数十秒かかる。この間にユーザーが除外ルールを追加/削除した場合に備え、ルールの読み直しは**②のplaylistロックを取得した後**に行う（撮影日マップはステップ6の結果をそのまま流用し、遡ってEXIFは読み直さない）。当初（#61時点）はこの読み直しをplaylistロックの**外**で独立した段階として行っていたが、それだと「ルール読み直し」と「playlistロック取得」の間に隙間ができ、その隙間に `exclude_image`（file/date即時反映。DB書込→playlist更新の順）が割り込むと、読み直したルールにはまだ反映されていないのに`exclude_image`側は既にplaylistから該当画像を消した直後、という食い違いが起き、除外したはずの画像がplaylistへ再追加されてしまう競合があった。読み直しをplaylistロック取得後に行うことで、`playlist_mutex`の総順序により競合が構造的に無くなる（詳細は§6(a)）。

### ② プレイリスト構築（完全平等）

- メモリ上に既存プレイリストが**無い**場合（`restore_playlist` が復元できなかった/まだ呼ばれていない場合。`is_same_directory` 判定はディレクトリ比較を `commands::playlist_persistence::normalize_directory_key` の正規化キーで行う。#62レビューS2）、まず `Database::load_playlist_state` で保存済み状態を読む。`directory_path` が今回のスキャン対象と一致すれば `Playlist::from_persisted` で復元し、「含めるべき集合」との差分を `update_images` 相当で適用して続きから再開する（#62）。一致しない、または保存が無ければ `Playlist::new` で新規シャッフルする。
- メモリ上に既存プレイリストが**ある**（同一ディレクトリの再スキャン。`restore_playlist` で先に復元済み、または同じディレクトリを2回目以降スキャンした場合）なら、現在のプレイリストのメンバーシップ（`Playlist::current_paths`）と「含めるべき集合」の**差分**を取り、`update_images(added, removed)` で更新する（#61 M2: 「物理的な新規/削除」ではなくこの差分を使うことで、除外ルールが新たに付いて対象外になったファイルも、物理削除されたファイルも同じ経路で正しくプレイリストから外れる。逆にルールが外れて対象に戻ったファイルは新規追加として扱われる。同じパスのまま `mtime` だけ変わった modified ファイルはこの差分に現れないため重複追加されない）。
- いずれの経路でもシャッフルが確定した（新規/復元後の差分適用/差分更新のいずれも `shuffled_list` が変わりうる）ので、`Database::save_playlist_full` で `shuffled_list`/`next_index`/`history`/`history_position` を1トランザクションでフル保存する（#62）。差分が空（メンバーシップに変化なし）の場合はこの保存を省略する。
- スキャン後、`last_directory_path` を DB に保存する。

### ③ スライドショー再生（フロント）

1. 起動時、`App.tsx`（`src/lib/startup.ts::runStartupSequence` に委譲、#62レビューS1）がまず `restorePlaylist()`（引数なし。対象はDB保存済みの前回フォルダ、#93）を呼ぶ。**成功すれば `rescanLastDirectory`（`rescan_last_directory`） の完了を待たずに** `useSlideshow.initialize` → 最初の `get_next_image` を呼んで即座に表示を始め、`rescanLastDirectory`（`rescan_last_directory`） はバックグラウンドで実行して完了後に `updatePlaylistInfo` で差分を反映する（10万枚規模だとスキャンに数秒〜数十秒かかりうるため、その間ずっと初期化画面のままにしない）。復元に失敗（保存が無い/ディレクトリ不一致/初回起動）した場合は、従来どおり `rescanLastDirectory`（`rescan_last_directory`） の完了を待ってから `initialize` する。プレイリストが復元されていれば保存済み `next_index` の続きから、無ければ最初の `advance` が index 0 から始まる（#62: 旧実装は最初の `advance` が index 0 を飛ばしていた）。
2. `useSlideshow` のタイマーが間隔ごとに `get_next_image` を呼ぶ（動画はタイマーでなく `onEnded`、または最大再生時間（#68）到達で次へ。§6-(h)）。
3. `get_next_image` は `Playlist::advance` で進め、新規画像かつファイル存在確認後にのみ表示回数を +1、5枚先までの先読み要求を単一ワーカー（`cache_worker.rs`）のキューへ投入する。現在画像のキャッシュ要求は先読みより優先して処理され、要求は重複排除・世代管理（新しい先読みバッチが来たら古い世代の先読み要求を破棄）される。`advance` 直後、巡の再シャッフルが起きた場合は `save_full`、それ以外は `save_position`（いずれも `commands/playlist_persistence.rs`）でプレイリスト状態を永続化する（#62、詳細は§6(a)）。
4. `←`/`→` キーや OverlayUI のボタンで前後移動。戻りは `get_previous_image` → `Playlist::go_back`（履歴は最大 `HISTORY_LIMIT`=100件、パスで保持するため再シャッフル境界をまたいでも実際に表示した画像を返す。戻り中の進行は表示回数を加算しない）。戻った直後も `save_position` で永続化する。
5. 画像表示時、`Slideshow.tsx` は `optimizedPath`（4K超/TIFF等/`apply_rotation=false`時の回転要求で必要になった場合のキャッシュ。まだ生成されていなければ原則原本をそのまま表示）があれば優先し、`convertFileSrc` でローカルファイルを表示する。`img` 要素は `crossOrigin`・`image-orientation` を明示指定せず、**回転は WebView 既定の動作（`image-orientation: from-image`＝EXIF Orientationに従って自動回転）に任せる**（#60 レビュー2巡目 must B。`crossOrigin="anonymous"` を付けて回転をCSSで明示切替する設計を検討したが、wry の WebKitGTK 実装が asset スキームを CORS 有効登録しておらず、付けると Linux 本番で画像が一切表示されなくなるリスクがあるため撤去した）。`apply_rotation=false` なのに EXIF が回転を要求している画像は、原本を返すと WebView が勝手に回転させてしまうため、バックエンド側が「格納画素のまま・EXIF無し」で書き出したキャッシュへ差し替える（`requires_synchronous_cache` が true の間は原本を返さず変換完了を待つ）。TIFF等 WebView 非対応形式も同様に変換完了を待つ。この待ちは `tauri::async_runtime::spawn_blocking` に逃がし、非同期コマンドの実行スレッドを塞がない。4K超のみが理由のキャッシュは非同期（先に原本を返してよい）。

### ④ ピック / 除外 / ignore の反映

- **ピック**: `pick_image` が原本をピック先フォルダへコピー（原本は変更しない）。
- **除外（file）**: `exclude_image` が `globset::escape` した除外ルールを DB に追加し、即座にプレイリストからも除去 → その場で反映。`update_images` の直後に必ず `playlist_persistence::save_full` でフル保存する（#62レビューM2(must): 保存し忘れると、再起動を跨いだときに除外したはずの画像がDB上の保存済みプレイリストから復活し、以後の巡で再び表示されてしまっていた）。
- **除外（date）**: `DateTimeOriginal` 優先で取得した撮影日を `rule_type="date"` で DB に登録し、`exif_cache` で既に該当日と分かっている画像があれば即座にプレイリストから除去する（こちらも同様に `update_images` 直後に `save_full` する、#62レビューM2）。exif_cache に無い（まだ一度も表示していない）画像は次回スキャンでのEXIF再取得を待つ。
- **除外（directory）**: `globset::escape` した親フォルダパス+`/**`（再帰的除外）を DB に登録するが、反映には再スキャンが必要。
- **ignore ルールの編集**: 追加/削除はすぐ DB に保存されるが、走査結果への反映は次回スキャン時。そのため設定画面の除外ルールタブは、変更直後に「再スキャンが必要」の案内と「今すぐ再スキャン」ボタン（引数なしの `rescan_last_directory`）を出す（#111。自動再スキャンはしない。案内と再スキャンの進行状態は `App` が `useExcludeRescan` フックで保持して `Settings` へ渡す（`Settings` は開くたびに key で再マウントされるため、閉じて開き直しても残る。スキャン全般の単一ガードも兼ね、除外ルールタブの再スキャンとフォルダタブのスキャンは並走しない）＝タブを往復しても二重実行・完了表示の取りこぼしが起きない。変更は1件の案内に集約し（2件以上は総称文言、追加→削除で元に戻れば案内は消える）、「フォルダ」タブの手動スキャン成功か案内のボタンでの再スキャン成功で消える。再スキャン中に入った変更は、その再スキャンに間に合っていないので完了後も残す。完了/失敗の表示は除外ルールタブを離れると消える。履歴タブのフォルダ/撮影日除外＝`needsRescan` も同じ案内に連動する）。手動追加（`add_ignore_pattern`）は `Glob::new` で検証し、不正なパターンは登録前に `Err` を返す（UIにもエラーメッセージを表示する）。
- **除外は削除ではない**: 除外ルールで対象外になったファイルは `file_metadata`/`image_stats`（表示履歴）が消えない。プレイリストからのみ外れ、ルールを解除すれば次回スキャンで復帰する（詳細は §6(c)）。
- **撮影日の遅延取得**: `get_next_image`/`get_previous_image` が画像を表示する際、EXIFから読んだ撮影日を `exif_cache` へ書き戻す（無い場合も `NULL` で記録）。次回以降のスキャンでは、その画像が撮影日ルールに一致すれば正しく除外される（詳細は §6(c)）。

### ⑤ 全データ初期化（`reset_all_data`、#64）

設定画面の「すべてのデータを初期化」（`InfoSection.tsx`）から呼ばれる。旧実装は DB ファイル自体を `remove_file` していたが、実行中の Tauri プロセスが同じ接続を保持し続けたまま別プロセスがファイルを掴んでいる環境（Windows 等）ではファイル削除に失敗しうる不安定さがあったため、**DB ファイルは削除せず接続を開いたまま中身だけ空にする**方式に変更した。ピック済みの画像ファイル（ピック先フォルダの実体）は対象外で、削除しない（DB上のメタデータのみ初期化する設計。詳細は `docs/user-guide.md`）。

DBリセット・メモリ状態クリア・キャッシュクリアの中核ロジックは `commands::system::reset_core`（Tauri非依存の`pub fn`）に切り出してあり、`reset_all_data`コマンド本体と`tests/reset_all_data_e2e.rs`の両方が同じ実装を呼ぶ（#79レビューshould4: テストがロジック本体の変更に自動的に追従するように、手でロジックを再現しない）。

1. **スキャンとの排他**: スキャンコマンドと同じ `ScanGuard`（`AppState::scan_in_progress`）を取得する。スキャン中に呼ばれた場合、および初期化中にスキャンが開始されようとした場合のどちらも `Err("scanInProgress")` で拒否する（#80: 文言でなくエラーコード。フロントが `t('errorScanInProgress')` でロケールに応じた文言へ変換する）。
2. **DBロックを取得し、`app.restart()`まで保持し続ける**（#79レビュー nit）: `state.db.lock()`のガードを`reset_core`の呼び出しと`app.restart()`の両方に跨いで保持する。全DBコマンドは`#[tauri::command] async fn`でtokioのワーカースレッド上で実行されるため、このロックを握ったまま`app.restart()`がスレッドをブロックし続けても、他のasyncタスクはロック獲得待ちでpendingになるだけでtokio自体は他のワーカースレッドで動き続ける（互いに相手のロックを待つ循環が無いためデッドロックにはならない）。ロックを早期に解放していた旧実装では、reset直後・プロセス実終了前のごく短い間に処理中だった`get_next_image`等（表示回数の加算・`exif_cache`の書き戻し）が古いパスの行をリセット後のDBへ書き戻せてしまう余地があった。
3. **`reset_core`本体**:
   1. `Database::reset_to_defaults` が全ユーザーデータテーブル（`database.rs`の`USER_TABLES`定数。#79レビューshould3で配列化し、`sqlite_master`の実テーブル一覧との一致をテストで検証する）を1トランザクションで空にし、`sqlite_sequence`（`scan_history.id`のAUTOINCREMENT採番カウンタ）もクリアしてから既定除外ルールを再投入する（`PRAGMA user_version`・スキーマは維持。§3 `database.rs` 参照）。`app_settings` も対象に含むため、`last_directory_path`/`apply_exif_rotation`/`share_directory_path`/`display_interval` 等のユーザー設定もすべて既定値へ戻る。
   2. **メモリ状態のクリア**: `AppState.playlist` を `None` に、`AppState.directory_path` を `None` にする。
   3. **キャッシュクリア**: `clear_cache_dir`（起動時クリアと共通、§6(d)）でキャッシュディレクトリの中身を退避→再作成する。`cache_dir`は`AppState::cache_dir`（起動時に一度だけ解決され、以後変わらないフィールド）をそのまま使い、ここでは追加のfallibleなパス解決を一切行わない（#79レビューshould1: 旧実装はDBリセットの**後**に`app.path().app_data_dir()`を呼んでおり、それが失敗するとDBは空なのにアプリは再起動しない不整合な状態になりえた。フィールドアクセスは失敗し得ないため、この問題は構造的に起きなくなった）。rename自体は同期的に完了するため、直後にプロセスを再起動しても取りこぼさない。
   4. **失敗セットのクリア**: `CacheWorker::clear_failed` で変換失敗の記録も消す。
4. **プロセスの再起動**: `app.restart()` を呼ぶ（2番で取得したDBロックを持ち越したまま）。

**4番の設計に落ち着くまでの経緯**: 当初は上記3のみ行い、`AppState.directory_path` に残しておいた旧スキャン対象へ `app.asset_protocol_scope().forbid_directory(dir, true)` を呼んで asset scope から明示的に取り消し、フロントは軽量な `window.location.reload()` だけで済ませる設計だった（`forbidden_patterns` は `allowed_patterns` より常に優先判定されるため、机上では取り消しが機能するはずだった）。しかしテストで実測したところ、**一度 `forbid_directory` したディレクトリは、その後同じディレクトリへ `allow_directory` を呼んでも `is_allowed` が `false` のまま戻らない**（forbidden が恒久的に優先され続け、取り消す API が無い）ことが判明した（`src-tauri/tests/reset_all_data_e2e.rs` のコメント参照）。これは「初期化→同じフォルダを選び直す」というごく普通の操作をしただけで、そのフォルダの画像が二度と表示できなくなる実装バグだったため撤回した。

代わりに `app.restart()`（`AppHandle::restart`、戻り値は `!`＝絶対に戻らない。tauri 2.12.0 でも同一を確認）でプロセス自体を再起動する方式にした。asset scope・`AppState` のメモリ状態はどちらも新規プロセスとして最初から構築されるため、この問題は原理的に起きない。`app.restart()` はメインスレッド上での呼び出しなら新プロセスを spawn してから `exit(0)`、そうでなければ `RunEvent::ExitRequested`/`Exit` をトリガーしてこの呼び出し自体はスレッドをブロックし続ける（イベントループが実際の終了処理を担う）。

**`tauri dev` 実行時の挙動について（#79レビューshould2、未検証）**: `tauri-cli` の dev は、アプリプロセスの終了時に `beforeDevCommand`（vite dev server）ごと kill する可能性が高い。もしそうなら、dev環境で本コマンドを呼ぶと dev server ごと停止し、再起動後のウィンドウが白画面のまま戻ってこない事故になりうる。この挙動はまだ実機確認していない。**実機での動作確認は `tauri dev` ではなく `tauri build`（`--debug` も可）が生成する、単体で完結した実行ファイルに対して行うこと。**

フロント（`InfoSection.tsx`）は確認ダイアログ（「完了後アプリが再起動します」と明記）→`resetAllData()` の順に進むだけで、成功時に追加で行う処理は無い（`window.location.reload()` は呼ばない）。バックエンドが成功時にプロセスごと再起動するため、この `invoke` 呼び出しは通常戻ってこない。`resetAllData()` が reject した場合のみ日本語のエラーメッセージ（Tauri commandの `Result<_, String>` をそのまま表示）を出し、ボタンを再度有効化する。

## 6. 主要な設計判断

### (a) 完全平等ランダムを `Playlist` に隔離する

ランダム性の中心ロジックを `playlist.rs` の `Playlist` struct 1か所に閉じ込めています。`shuffled_list`（シャッフル済み全画像）を先頭から順に消費し、末尾に到達したら再シャッフルすることで、**1巡するまで同じ写真は二度出ない**＝全画像が均等に表示される、を構造的に保証します。再シャッフル時は「直前に表示した画像が新しい巡の先頭に来たら2番目と入れ替える」ことで、巡の境目での連続表示も防いでいます。前後移動は `history`（最大 `HISTORY_LIMIT`=100件）＋`history_position` で扱い、`advance` は戻った先から再び新規へ進むときだけ表示回数を加算します（履歴内の再表示は重複カウントしない）。このロジックを 1 struct に隔離しているため、平等性の単体テストが容易で（`playlist.rs` 内にテストあり）、IPC・画像処理・UI から独立して検証・変更できます。

**進行カーソルは `next_index`（消費済み件数）で持つ（#62レビューM1 must）**: `Playlist` は「最後に表示した位置」を表す `current_index` と、開始前を表す `before_start: bool` の2状態を同期させる旧設計を廃し、単一の `next_index: usize`（範囲 `0..=len`）だけで持つ。`shuffled_list[0..next_index)` が「今の巡で表示済みの区間」、`[next_index..)` が「未表示の区間」という1つの不変条件だけで、開始前（`next_index==0`）・巡の末尾（`next_index==len`）の両方を表せる。旧設計は `update_images` の削除処理で「表示中の画像自身が削除された」場合の補正（`[..current_index]`、表示中の画像自身を含まない）が1件不足しており、削除後にその位置へスライドしてきた未表示画像を「表示済み」扱いにして1枚飛ばすバグがあった。`next_index` なら削除件数を `[..next_index]`（表示中の画像自身を含む）で数えるだけで過不足なく補正できる。

**履歴はパスで保持する（#62）**: `history: Vec<String>`（旧実装は `Vec<usize>`、シャッフル済みリストのインデックス）。末尾到達時の再シャッフルで `shuffled_list` の並びが丸ごと変わるため、インデックス保持だと再シャッフル境界をまたいで `go_back` した際に「そのインデックスに今たまたまある別の画像」を返してしまう。パスで保持すれば、シャッフル後も常に実際に表示した画像そのものを指し続ける。`next_index`（`shuffled_list` を消費していく進行カーソル）は `go_back` では変更せず、履歴内を戻ってから再度 `advance` したときに正しい続きの位置から前進できるようにしている。

**永続化は2テーブル・シャッフル確定時のみフル保存、それ以外は軽量更新（#62、#62レビューM3 must）**: 10万件規模だと `shuffled_list` の JSON は大きく（数MB）、毎 `advance`（表示間隔5〜60秒ごと）にこれを含む行を書き直すと、SQLiteは行全体をコピーして書くため実測で1回あたり数十ms・1日あたり数十GB相当の無駄なI/Oになる。そこで永続化先を書込頻度で2テーブルに分ける: `playlist_list`（`directory_path`/`shuffled_list`、シャッフル確定時＝新規作成・巡の再シャッフル・`update_images` によるメンバーシップ変更のときだけ書く）と `playlist_position`（`next_index`/`history`/`history_position`、`advance`/`go_back` のたびに書く軽量な `UPDATE`）。`Playlist::advance` の戻り値に「このadvanceで再シャッフルが起きたか」を含め、呼び出し元（`commands/playlist_persistence.rs::save_full`/`save_position`）がどちらを呼ぶか判断する。保存に失敗しても表示は継続させ、`eprintln!` でログするだけにする（#62レビューS3: `let _ =` で握りつぶさない）。

**メンバーシップ変更は必ず保存とセット（#62レビューM2 must）**: `Playlist::update_images` を呼ぶ箇所（`perform_scan` の差分更新・起動時復元、`exclude_image` のfile/date即時反映）は、呼んだ直後に必ず `playlist_persistence::save_full` を呼ぶ。`exclude_image` は当初これを怠っており、除外した直後にアプリを再起動すると、除外したはずの画像がDB上の保存済みプレイリストから復活し、以後の巡で再び表示されてしまっていた。

**起動時の復元は独立コマンド `restore_playlist`（#62レビューS1、元issue問題1）**: 10万枚規模かつ表示間隔次第では1巡に何日もかかりうるため、起動のたびに再シャッフルしていると「毎日再起動する運用」では1巡が終わらず完全平等が成立しない。当初はスキャン（`perform_scan`）の中だけで復元していたが、それだとスキャン完了（10万件規模で数秒〜数十秒）を待たないと最初の画像すら出せない。`restore_playlist` コマンドを独立させ、フロントは起動直後にまずこれを呼んで `Database::load_playlist_state` から即座に復元し（`directory_path` が一致する場合のみ、`AppState.directory_path` もここで設定する）、成功すればスキャン完了を待たずに表示を始め、スキャンはバックグラウンドで実行して差分だけ後から反映する。復元できなかった場合（保存が無い/ディレクトリ不一致/後述のディレクトリ不在/スキャン中）は スキャン内の復元ロジック（同じ `load_playlist_state`/`from_persisted` 経路）がフォールバックとして働く。ディレクトリの一致判定は `commands::playlist_persistence::normalize_directory_key`（`canonicalize` 優先、失敗時は末尾区切り除去）で行う（#62レビューS2）。保存は常に1行のみのため、フォルダA→B→Aと切り替えるとAの途中経過は上書きされて失われる（複数フォルダの状態を同時保持しない設計、詳細は `docs/features.md`）。

**`restore_playlist` はディレクトリの存在確認をしてから復元する（#62レビュー2巡目 N-M1 must）**: NAS/USBが未マウントのまま起動した場合など、保存済みプレイリストが指すディレクトリに今アクセスできないことがある。これを確認せず復元してしまうと、保存されていた画像のほぼ全てが「実ファイルが無い」状態になり、`get_next_image` が（後述のN-S1のリトライ機構によって）`advance` を延々と繰り返しながら誰にも見せないまま巡全体を無言で消費してしまう（＝実質的にその巡を丸ごと失う）。`perform_restore` は `sanitize_allow_dir` でディレクトリの実在・絶対パス・非保護ルートを確認し、失敗すれば復元せず `rescan_last_directory` 側のフォールバック（=スキャンして0件で気づく、通常のエラー導線）に委ねる。

**`restore_playlist` の呼び出し前提（#62レビュー2巡目 N-S2、#62レビュー3巡目 nit で強化）**: `playlist_mutex` が既に `Some`（別経路で既に初期化済み）で、かつ `directory_path_mutex` が今回リクエストされたディレクトリと一致するなら、何もせず「既存維持」で `true` 相当（`RestoreOutcome::AlreadyReady`）を返す。一致しない（例: 別ディレクトリへの切替直後で古いディレクトリのプレイリストがまだ残っている）場合は「既存維持」を騙らず `NotRestored` を返す。`scan_in_progress` が立っている間（スキャン実行中）は `false` 相当（`NotRestored`）を返し、スキャンの完了に任せる。**#62レビュー3巡目 nit(TOCTOU対策)**: `playlist_mutex` の `is_some` 確認から実際に `Some(playlist)` を設定するまで、同じ `MutexGuard` を関数の最後まで保持し続ける（確認と代入の間に別スレッドの `perform_restore`/`perform_scan` が割り込む隙を無くす）。`db_mutex`/`directory_path_mutex` はこの `playlist_mutex` ロックを保持したまま内側で取る（順序は playlist→db／playlist→directory_path。`perform_scan` の Stage 4 や `commands/image.rs` の永続化と同じ順序で、逆順は無いためデッドロックしない）。

**`get_next_image`/`get_previous_image` は消えたファイルを内部で読み飛ばす（#62レビュー2巡目 N-S1、#62レビュー3巡目 T-M1/S-bで精緻化）**: 実ファイルが後から消えている（NAS切断・USB取り外し・外部ツールでの削除等）画像に `advance`/`go_back` で当たった場合、以前は即座に `Ok(None)` を返し、フロントは「No more images」のエラー画面にフォールバックしていた（1件消えているだけでスライドショーが止まって見えてしまう）。`MAX_MISSING_FILE_SKIPS`（20）を上限に内部でさらに次/前へ進み直し、最初に実在する画像が見つかったものだけを返すよう変更した。消えたファイルは次回スキャンでプレイリストから除去される（母集団自体から外れる）ため、ここで飛ばしても「1巡で全件ちょうど1回」という完全平等の保証には影響しない。表示回数は実在が確認できた画像1件にのみ加算する（従来どおり）。上限は、フォルダごとアンマウントされた等の異常事態で無限ループにしないための安全弁で、到達時は `ImageNavigationResult::LoadFailed` を返す（#65。旧実装は `None` だった。フロントは `loadFailed` を受けたら自動でもう一度呼び直す＝連続失敗上限つきの自動読み飛ばしを行う）。

**`get_next_image`/`get_previous_image` はループの各反復でディレクトリ自体の生死も確認する（#62レビュー3巡目 T-M1 must）**: `MAX_MISSING_FILE_SKIPS` の上限は「個々のファイルが飛び飛びに消えている」通常のケースを想定したものであり、スキャン対象ディレクトリ自体（NAS/USB）が丸ごと外れている場合にそのまま適用すると、`advance` するたびにほぼ確実にファイルが見つからず、鑑賞中に数秒おきに呼ばれる `get_next_image` のたびに毎回上限（20件）ぶん未表示画像を無駄に消費してしまう（1回の呼び出しで最大20倍の消費速度になる）。ループの各反復の直前に `directory_root_is_accessible`（`AppState.directory_path` の `Path::is_dir()`）でルート自体の存在を確認し、無ければその回は一切 `advance` せず即座に `ImageNavigationResult::RootUnavailable` を返す（#65。旧実装は `None`）。フロントはこれを受けたら鑑賞中の画像を消さずに維持し、控えめな再接続待ち通知を出す。`directory_path` が未設定（テスト等）の場合はチェック対象が無いとみなし許可する。

**`get_next_image`/`get_previous_image` はファイル欠損とキャッシュ変換失敗を区別する（#62レビュー3巡目 S-b）**: `get_image_info_internal` の戻り値を `ImageLookup::{Found, Missing, ProcessingFailed}` の3値にした。`Missing`（ファイルが存在しない、軽い）はループで次のファイルへ読み飛ばしてよいが、`ProcessingFailed`（存在はするがキャッシュ変換が失敗/タイムアウト。`request_current_and_wait` が最大 `CACHE_WAIT_TIMEOUT`＝既定5秒待つ）は同じ扱いにしない。もし区別せず両方とも読み飛ばしていたら、同じ理由（壊れたファイル群等）で何枚も連続して同じ待ちが発生した場合に最悪 `MAX_MISSING_FILE_SKIPS × CACHE_WAIT_TIMEOUT`（20×5秒＝100秒）ブロックしてしまう。`ProcessingFailed` はループで繰り返さずその場で `ImageNavigationResult::LoadFailed` を返して打ち切る（#65。旧実装は `Ok(None)`）。

**`AppState.directory_path` はplaylistロックを保持したまま更新する（#62レビュー2巡目 nit）**: `perform_scan` は最終的に `directory_path_mutex`（`AppState.directory_path` 相当）へ今回スキャンしたディレクトリを書き込むが、これを呼び出し元（`scan_chosen_directory`）が `perform_scan` の**戻り値受領後**に別途行っていた旧実装だと、「Stage完了〜directory_path更新」の間に小さな窓ができ、その間に他コマンド（`get_next_image`/`exclude_image`）が軽量保存すると、古いディレクトリパスを `playlist_list.directory_path` へ書いてしまうおそれがあった。`perform_scan` はplaylistロックを保持したまま `directory_path_mutex` も同じ区間内で更新することでこの窓を無くしている。

**`update_images` の位置補正とランダム挿入（#62、#62レビューM1）**: 削除は `next_index` より前（`[0, next_index)`。表示中の画像自身を含む今の巡の表示済み区間）にあった件数だけ `next_index` を減算し、削除ぶんだけ未表示画像を飛ばすことを防ぐ。新規画像は「未再生区間」（`next_index` 以降。何も表示していなければ全体）の中にランダムな位置で散らして挿入する（既存の未再生区間と新規画像をそれぞれの相対順序を保ったまま件数比でインターリーブする1パスのマージ、O(N+K)）。末尾へ塊で追加すると、その巡の終盤に新規画像が連続して固まって出てしまうため。

**`peek_next_n` は巡の境界で打ち切る（#62）**: 先読み（5枚先までキャッシュ）のための覗き見は、`next_index + n` が `shuffled_list` の範囲を超えたら `None` を返して打ち切る（次巡の並びを前倒しで確定させて覗く方式ではなく、単純な打ち切りを選んだ。`n=0` が次に表示される画像に対応する）。次巡の並びは実際に `advance` が末尾へ到達するまで確定しないため、先読みのために先読みで確定させると「境界での連続表示回避チェック」より前に並びが固まってしまう複雑さがある。巡の残りが5枚未満なら先読みキャッシュの枚数が一時的に減るだけで、表示自体には影響しない。

### (b) 差分スキャン（mtime）

10万枚規模では毎回の全走査と全 DB 書き込みは重いため、`scanner.rs` は前回のファイルメタデータ（パス→`mtime`。`size` も保持しますが変更判定には使いません）と突き合わせて差分だけを処理します。前回無かったパスは新規（`new_files`）、既存パスで `mtime` が変わったものは変更（`modified_files`）として区別し、どちらも DB へ upsert します。消えたファイルは削除として DB から除去します。これにより 2回目以降の起動が高速になります。

**差分比較の対象はスキャン対象ディレクトリ配下だけ（#63）**: 前回メタデータの取得は `Database::get_file_metadata_under(directory)` で、今回スキャンするディレクトリ配下のパスだけに限定します。以前は `get_all_file_metadata`（DB全件）を基準にしていたため、複数フォルダを切り替えて使う運用（フォルダA→B→A）で、Bをスキャンした時点でAのファイルが「今回の生スキャンに存在しない」と誤判定され確定削除されてしまう事故がありました。境界判定は区切り文字での前方一致（`LIKE ... ESCAPE`）で行うため、`/photos/a` を対象にしても `/photos/abc` のような別ディレクトリを巻き込みません。

**`walkdir`/メタデータ取得エラーは「不明」として扱い、削除しない（#63）**: `walkdir` の読み取りエラー（権限拒否等）や、ファイル単位の `fs::metadata`/`mtime` 取得エラー（1970-01-01より前のmtimeで `duration_since` が失敗するケースを含む）は、以前は黙って結果から除外され、そのファイルが「消えた」ように見えてしまっていました。`scanner::ScanError { path, message }` として件数・代表例（最大5件）を収集し、`ScanResult`/`ScanProgress` に反映してUI（設定画面のスキャン結果）にも表示します。エラーが起きたパス（ディレクトリの場合はその配下すべて）は確定削除ではなく「不明」（`unknown_files`）として扱い、`file_metadata`/`image_stats`/`exif_cache` を保持します。また、エラーが発生しても進捗コールバックの処理件数は必ず進めるようにし、以前は成功時にしかカウントしていなかったため一部エラーが混ざると `count` が `total` に到達せず最終進捗イベント（`scan-progress`）が発火しないことがあった不具合も修正しました。

**Stage3のfile_metadata反映はバッチ化・1トランザクション化（#63）**: 以前は生スキャンで見つかった全ファイル（10万件規模なら10万件。大半は「変更なし」）を毎回1件ずつ `upsert_file_metadata` していましたが、実際にDBへの反映が必要なのは新規/変更分だけです。`Database::apply_file_metadata_changes(upserts, deleted_paths)` が新規/変更分のみのupsertと確定削除分の削除を1トランザクション・`prepare_cached`（準備済みSQL文の使い回し）でまとめて反映します。`perform_scan` はこのDBロック区間の保持時間を計測し、100msを超えたら `eprintln!` で記録します（実測値は下記参照）。

**#63計測**（releaseビルド・ローカルSSD上、macOS）: `tests/db_reflection_throughput.rs`（`#[ignore]`）で、10万件の合成パス配列を直接 `apply_file_metadata_changes` に与えて計測すると、新規10万件upsertが約0.18秒（約57万件/秒）、全10万件を変更ありとして再upsertが約0.21秒（約48万件/秒）、5万件の確定削除が約0.11秒（約44万件/秒）。`tests/scan_reflection_throughput.rs`（`#[ignore]`）で実ファイル**10万件**を敷いて `perform_scan`（WalkDir〜DB/playlist反映まで）を計測すると、初回scan（全件新規）が約0.83秒（約12万件/秒。Stage3のDBロック保持時間は約459ms）、差分なしの再scan（file_metadataへの書込0件）が約0.39秒（約26万件/秒）。いずれも `cargo test --release -- --ignored --nocapture <test名>` で再測定可能（フィクスチャが小さくOSページキャッシュに乗り切るため、実運用のNAS越しアクセスや数MB級の実写真ではこれより低下する）。

**修正前との比較（PR#77レビューM4、DB反映単体での比較）**: Issue #63に記録された修正前の実測値は、バッチ化前の「毎ファイル`upsert_file_metadata`（暗黙のautocommit、1件＝1トランザクション）」方式で5,000件upsertに1.8秒（約2,780件/秒）。この比較はいずれもDB反映（upsert）単体の速度であり、`perform_scan`一気通貫（WalkDir＋DB/playlist反映）の比較ではない点に注意。`apply_file_metadata_changes`（1トランザクション＋`prepare_cached`）による新規10万件upsert（約57万件/秒、同じくDB反映単体）は、単純な件数あたりの速度比較で約**200倍**。10万件規模に単純外挿すると旧方式はDB反映だけで数十秒（`100,000 ÷ 2,780 ≒ 36秒`）かかっていた計算になり、`perform_scan`一気通貫（WalkDir込み）でも1秒未満に収まる新方式との差は体感できるレベルの改善。

### (c) ignore パターン

除外ルールは DB の `ignore_rules` テーブル（`pattern` + `rule_type`。主キーは `(pattern, rule_type)` の複合キー。同一文字列の glob ルールと date ルールが共存できるように #61 で変更）に永続化し、2種類を区別します。

**`rule_type = "glob"`（通常のglobパターン）**

`globset` ベースの glob で表現します（`.thumbnails/`・`Thumbs.db`・`.DS_Store`・`@eaDir/`・`desktop.ini`・ドットフォルダなどを既定で投入）。マッチ判定はフルパスに加えて各パスコンポーネント単位でも行うため、フォルダ名だけのパターン（例: `private`）でも階層途中のフォルダを除外できます。

末尾が `/`（Windows手入力の `\` も同様）のパターン（`**/.thumbnails/` 等）は特別扱いします。**globset は `**/name/`のようなパターンを、末尾が文字どおり`/` で終わる文字列にしかマッチさせません**が、`walkdir`が列挙するのは常にファイルであり、そのパス文字列が`/` で終わることはないため、実測ではこの形の既定ルールは一切マッチしませんでした（#61 で発覚。globset 0.4.18 で実機検証済み、`ignore.rs`のテストに残しています）。修正として`normalize_dir_pattern`が末尾`/`/`\` パターンを `**/{name}/**` に正規化し（手入力で `**/` が重なっていても剥がしてから正規化するため二重にはならない）、「祖先ディレクトリのいずれかの名前が `name` と一致するか」という判定に置き換えます。この判定は**スキャンルートからの相対パス**に対して行います。フルパスに対して行うと、スキャンルート自体がドットディレクトリ配下にある場合（例: `~/.photos/` をスキャン）に、ルート自身の名前のせいで配下の全ファイルが誤って除外されてしまうためです。既存DBに保存済みの同じパターン文字列（例 `**/.thumbnails/`）は変更していません。判定ロジック側の修正だけで新しい挙動が効くため、ignore_rules テーブルへのデータ移行は不要です。

ファイル/ディレクトリ単位の除外（`exclude_image` の `file`/`directory`）は、対象パスを `globset::escape` してから glob として登録します。エスケープしないと、`photo[1].jpg` や `dir [2020]/` のようにパスにglobのメタ文字（`[`,`]`,`{`,`}`,`*`,`?`）が含まれる場合に自分自身へマッチせず、除外したはずのファイルが除外されないというバグがありました（#61）。`directory` は `{escaped}/**` として登録し、直下だけでなくサブフォルダ配下も再帰的に除外します。旧実装の `{parent}/*` は、globset のデフォルト設定（`literal_separator` 無効）では実は `*` も `/` をまたいでマッチするため実際にはサブフォルダも含めて除外できていましたが、そのことはコード上まったく自明ではなく意図が伝わらないため、`/**` という明示的な表現に変えて意味を明確にしました（#61レビュー: 「直下しかマッチしていなかった」という当初の認識は誤りで、実質的な動作は変えず可読性のための変更です）。手動追加（`add_ignore_pattern`、設定画面の除外ルールタブ）は `Glob::new` で構文検証し、不正なパターン（閉じていない `{` など）は `Err` を返して UI にエラーを伝えます（旧実装は `eprintln!` で握りつぶし、UI には成功したかのように表示していました。設定画面側もエラーメッセージを表示するようにしています）。

**`rule_type = "date"`（撮影日除外）**

`exclude_image` の `date` は EXIF撮影日時（`DateTimeOriginal` → `DateTimeDigitized` → `DateTime` の優先順、#61。`DateTime` 単体は「最後にファイルを書き換えた日時」であり実際の撮影日とずれることがあるため。`display_value()` が返す `"unknown"` のようなプレースホルダはこのタグが未設定という扱いにして次の優先タグへフォールバックする）から `YYYY-MM-DD` を取り出し、`rule_type="date"` のルールとして登録します。旧実装は `*YYYY-MM-DD*` というパス文字列の部分一致globを生成していましたが、`IMG_0001.jpg` のようにファイル名に日付を含まない画像には原理的に一切マッチしないという欠陥がありました。

撮影日は独立テーブル **`exif_cache`**（`path` / `captured_date` / `file_mtime`）に保持します。`file_metadata` とは別で `mark_deleted`（物理削除の反映）の対象外にしているため、ファイルが一時的に消えても（USBメモリの取り外し等）撮影日キャッシュは失われず、ファイルが復活すれば `file_mtime` の一致を見て再利用されます。

10万枚規模の写真フォルダでは、スキャンのたびに全件の EXIF を読むとスキャン時間が大きく伸びてしまい、差分スキャンによる高速起動（§6(b)）という既存の設計方針と相容れません。そこで次の方式を採りました:

1. 表示時（`get_next_image`/`get_previous_image` → `get_image_info_internal`）に EXIF を読んだ際、撮影日を `exif_cache` へ書き戻す（無い場合も `captured_date=NULL` で記録し、同じ「日付なし」判定を繰り返さないようにする）。表示のために EXIF を読む処理は既存のもので、追加コストはDB書き込み1回だけ。
2. **スキャン時**、撮影日ルールが1件以上ある場合に限り、`exif_cache` に未取得、またはファイルの現在の `mtime` がキャッシュ時と食い違う（＝ファイルが変更された）候補だけを対象に、`rayon` で並列にEXIFを読み直し、結果を `exif_cache` へバッチ書き込みする。撮影日ルールが無ければ一切EXIFを読まない。
3. 上記1・2のいずれでも撮影日が得られなかった画像は、`extract_date_from_path` で**スキャンルートからの相対パス**中の `YYYY-MM-DD`/`YYYYMMDD` 表記を探し、見つかればそれで代替判定する。

この設計により、一度も表示していない画像でも、撮影日ルールが設定されていれば次のスキャンで（多くの場合は初回スキャンから）正しく除外されます。スキャン時に無条件で全件のEXIFを読む方式は採らず、撮影日ルールの有無で完全にオン/オフを切り替えることで、撮影日除外を使わないユーザーのスキャン速度には一切影響しません。

**S-b計測（#61）**: 上記2の中核である `resolve_captured_dates`（DB/Tauriを挟まない純粋関数）単体を、実 `DateTimeOriginal` 付きの極小JPEGフィクスチャ1000件・`exif_cache`全未取得（＝初回スキャン相当の最悪ケース）で計測すると、debugビルド・ローカルSSD上で約68,000〜77,000件/秒（`tests/exif_resolve_throughput.rs`、`cargo test --release -- --ignored --nocapture exif_resolve_throughput` で再測定可、このリポジトリではディスク制約からdebugビルドで実測）。フィクスチャは4x4px・数百バイトでOSページキャッシュに乗り切るため、これは並列読み出しパイプライン自体のオーバーヘッドが小さいことを示す上限値であり、実運用の数MB級写真やNAS越しのアクセス（レイテンシがローカルSSDと桁違い）ではこれより大きく低下する。撮影日ルール追加直後の初回スキャンが体感的に重くなる場合、原因はこの並列読み出し自体より画像サイズ・ストレージ経路（NAS等）である可能性が高い。

**除外は「削除」ではない**: `scanner.rs` は除外ルールを一切適用しない生スキャンを行い、`file_metadata` の新規/削除判定はその物理的な事実だけを基準にします（§5①）。除外ルールの適用は別段階（`IgnoreFilter`）として行い、結果は「プレイリストに含めるべき集合」の算出にのみ使います。プレイリストは「物理的な新規/削除」ではなく、現在のプレイリストのメンバーシップと「含めるべき集合」の差分で更新します（§5②）。この分離により、除外ルールを新しく追加/削除しても、対象ファイルの `file_metadata`/`image_stats`（表示回数・最終表示日時）は一切影響を受けず、スライドショーへの出入りだけが切り替わります。修正前は、除外ルールで対象外になったファイルがスキャン結果に一切現れなくなるため「物理的に削除された」と誤判定され、`mark_deleted` で表示履歴ごと消えてしまうバグがありました（#61）。「含めるべき集合」はプレイリスト反映の直前に除外ルールを読み直して計算するため、生スキャン・EXIF並列読みの実行中に追加/削除されたルールも取りこぼさない（#61レビュー S-1、詳細は §5①ステップ7）。

**確定削除と「不明」の区別はディレクトリの枝刈り・スキャンエラーで判定する**: `scanner.rs` の差分検出で「前回は追跡していたが今回の生スキャンに現れなかった」ファイルは、(1) `IgnoreFilter::has_pruned_ancestor_dir` で祖先ディレクトリが `WalkDir::filter_entry` により枝刈りされているか、(2) 今回のスキャンでそのパス自身またはその祖先が `ScanError` の対象になっていないか（#63）、のいずれかに該当すれば「不明」（`unknown_files`。存在確認できないので `file_metadata` を保持する）とし、どちらにも該当しなければ「確定削除」（`deleted_files`。`mark_deleted`/`apply_file_metadata_changes` の対象）とする。`filter_entry` はディレクトリしか刈らずファイルは常に列挙するため、ファイル単位のglob（特定ファイルパスの除外パターン等）で除外されているだけのファイルは、ディレクトリ自体が刈られていない限りWalkDirが探索済みであり、それでも現れなければ本当に消えたと判断できる（#61レビュー nit: 以前は `is_ignored`（ファイル単位のglobも含む）で判定しており、そのようなファイルが実際に削除されても「不明」扱いのまま `file_metadata`/`image_stats` が残り続けてしまっていた）。

**`get_recent_images` のスキャンルート解決**: 「最近表示した画像」は複数のスキャンルートにまたがりうるため、各画像パスに対して `get_distinct_scan_directories`（過去にスキャンした全ディレクトリ）の中から最も長く一致するものを探し、そのルートからの相対パスで `IgnoreFilter` を適用します。対応するルートが見つからない場合はフルパスをそのまま使う従来の判定にフォールバックします。絶対パスのままドットディレクトリ包括ルールなどを適用すると、ドットディレクトリ配下をスキャンしたライブラリの履歴が全消えするバグがありました（#61 S3）。

### (d) 画像最適化キャッシュは単一ワーカー + キューで直列化する

旧実装は `get_next_image`／先読み1件ごとに `thread::spawn` していたため、キーリピート等で数十本のスレッドが同時に巨大画像をフルデコード＋Lanczos3する事故があった（#60）。`cache_worker.rs` は常駐スレッド1本に置き換え、要求をキューで管理する：現在表示中の画像の要求は先読みより優先して処理し、新しい current 要求が来たら古い current は先読み優先度へ格下げする（同時に「現在画像」は1件だけという前提を保つ）。同じキャッシュファイルへの要求は重複排除、新しい先読みバッチが来たら古い世代の先読み要求（現在画像分は除く）を破棄する。書込は一時ファイル→`rename` でアトミックに行い（`exists()` が書込途中のファイルを返す事故を防ぐ）、合計サイズが上限（既定2GB、`CACHE_MAX_BYTES`）を超えたら更新日時の古いものから削除する。ただし直近に実際へ返した（表示に使った）パスは削除対象から除外し、キャッシュヒット時に mtime も更新するため、生成順（実質FIFO）ではなく真のLRUに近い。ジョブ処理は `catch_unwind` で囲み、image crate 内で panic が起きてもワーカースレッド自体は死なない。変換に失敗した画像はキー（cache_file）を失敗セットに記録し、同じキーの再要求（current/prefetch とも）を抑止する。

`request_current_and_wait`（同期待ち。下記参照）と、通知する側（ワーカーの `notify_completed`）は同じ `queue` ロックを取ってから確認/通知する。待ち手はロックを保持したまま「完了しているか」を確認してから `wait` するため、確認と待機開始の間に通知が来て待ちそびれる（lost wakeup）事故が起きない。

キャッシュ要否の判定（`image_processor::plan_cache_file`）は次のいずれかで、それ以外は原本をそのまま表示する:

- WebView が直接表示できない形式（TIFF等）
- 表示サイズが4K超（判定はヘッダ上の生の幅高さ＝回転前で行う。WebViewは原本をそのままデコードしてからCSSで回転を表示上適用するだけで、デコード時のメモリコストは回転の有無に関係ないため）
- `apply_rotation=false` なのに EXIF Orientation が回転/反転を要求している（詳細は下記(e)）

**EXIF回転が必要というだけで`apply_rotation=true`ならキャッシュを作らない**（回転は下記(e)の通りWebView既定の動作に任せる）。アニメーションしうる形式（GIF/WebP）は静止フレーム化を避けるため常に対象外とする。キャッシュキーには原本の mtime・サイズも含め、原本が置き換わった場合に古いキャッシュを誤って使い回さないようにしている。出力フォーマットはデコード後の実データのアルファ有無（`resized_img.color().has_alpha()`）で決める。キャッシュファイル名の拡張子はヘッダから軽量に見積もったアルファ有無（`source_has_alpha`）で先に決めており、両者は実質的に一致する。

原本をそのまま返すと表示が誤る2ケース（WebView が直接表示できない形式、または `apply_rotation=false` なのに回転が必要）は `image_processor::requires_synchronous_cache` が true になり、`CacheWorker::request_current_and_wait`（タイムアウト付き、既定5秒）で変換完了を同期的に待ってからキャッシュパスを返す。この待ちは `tauri::async_runtime::spawn_blocking` に逃がし、非同期コマンドの実行スレッド自体は塞がない。失敗・タイムアウト時は `get_image_info_internal` が `Ok(ImageLookup::ProcessingFailed)` を返し、呼び出し元（`get_next_image`/`get_previous_image`）はこれをループで読み飛ばさずその場で `ImageNavigationResult::LoadFailed`（#65。フロント側の自動スキップ自体も #65）に変換して打ち切る。4K超のみが理由の画像は原本もWebViewで表示できるため、これまで通り非同期（先に原本を返し、バックグラウンドでキャッシュを作る）。

ワーカーは単一スレッドで非プリエンプティブなため、`request_current_and_wait` 呼び出し時にワーカーが既に別の重い先読みジョブを処理中だと、それが終わるまで新しい current 要求は着手されない。巨大な先読み画像の処理中に呼ばれた場合、タイムアウト（既定5秒）を使い切る可能性がある（既知の制約）。

起動時・`reset_all_data` 双方のキャッシュクリアは `cache_worker::clear_cache_dir` に共通化した。`cache_dir` を退避ディレクトリ（`cache-trash-<timestamp>`）へ rename→空の `cache_dir` を再作成し、退避先の削除はバックグラウンドスレッドに任せる（rename はディレクトリエントリの付け替えのみで一瞬。この直後に動く `CacheWorker` の新規書込と競合しない）。呼び出しのたびに `app_data_dir` 直下に残っている古い `cache-trash-*`（前回クラッシュ等で消しきれなかった分）もまとめてバックグラウンド削除する。rename が失敗した場合（別ファイルシステム上にある等）は、中身を1件ずつ同期的に削除するフォールバックを行う（失敗した項目は無視して続行。rename成功時ほど高速・無競合ではない既知の劣化経路）。`reset_all_data` はキャッシュクリアに加えてワーカーの失敗セットもクリアする（過去の失敗記録が居座って同じ画像が以後ずっと再試行されなくなるのを防ぐ）。

### (e) 回転は WebView 既定の動作に任せ、フロントで明示切替しない（#60 レビュー2巡目 must B）

1巡目のレビューでは「回転はキャッシュに焼き込まず、フロントの `image-orientation` CSS を `apply_exif_rotation` 設定に連動して `from-image`/`none` に明示切替する」設計にし、asset プロトコルが別オリジンであることに対応するため `crossOrigin="anonymous"` も付与していた。しかし2巡目のレビューで、**wry の WebKitGTK 実装が asset スキームを CORS 有効登録しておらず、`crossOrigin` を付けると Linux 本番で画像が一切表示されなくなるリスク**があると指摘され、この明示切替自体を撤去した。

現在の設計:

- `img` 要素は `crossOrigin` も `image-orientation` も指定しない。回転は WebView 既定の `image-orientation: from-image`（EXIF Orientationに従って自動回転）にすべて任せる。`ImageInfo.applyRotation` フィールドはフロントで不要になったため削除した。
- `apply_rotation=true` の場合、回転が必要というだけでは原本のまま返してよい。WebView が EXIF に従って正しく回転表示するため。
- `apply_rotation=false` なのに EXIF が回転を要求している画像だけは例外で、原本をそのまま返すと WebView 既定の `from-image` が勝手に回転してしまい設定（OFF）と食い違う。この場合はバックエンドが「格納画素のまま・EXIF無し」で書き出したキャッシュに差し替える（`optimize_image_for_4k(path, false)` は回転を適用せず、再エンコードでEXIFも失われるため、結果的に「回転なし」を保証できる）。この差し替えは (d) の同期待ち経路を使う。
- 4K超/TIFF等で `apply_rotation=true` として結局キャッシュが焼かれる画像は、生成時に画素を回転しEXIFなしで書き出す。`from-image` を当てても（EXIFが無いので）二重回転はしない。
- 動画・地図タイル（OverlayUI の OSM 画像）はこの変更と無関係（別要素・別ファイル）。
- **既知の制約**: アニメーションしうる形式（GIF/WebP）はキャッシュ対象外のため、EXIF の回転タグ付きの WebP は「EXIF回転」設定をオフにしても WebView が回転して表示します。 Linux は `image-orientation` の既定が `from-image` になる WebKitGTK 2.30 以降を想定する。設定画面のサムネイル（`thumbnail.rs`）は設定に関わらず常に向きを焼き込む。

### (f) スライドショー進行のフロント状態管理を再設計する（#65）

`useSlideshow`/`App.tsx`/`Slideshow.tsx` はIssue #65で全面改修した。主な設計判断:

- **`isPlaying` はフックの内部状態でなく `App.tsx` が導出する派生値にする**:
  `isPlaying = isInitialized && !isPausedByUser && !isOverlayHovered && !isSettingsOpen`。
  旧実装は `useSlideshow` が `isPlaying` を持ち `play()`/`pause()` で外から書き換えて
  いたため、`initialize(true)` のような「初期化ついでに再生開始」の呼び出しが、
  設定画面が開いていても構わず再生を始めてしまうバグ（設定画面で再スキャンすると
  裏でスライドショーが進む）があった。派生値にすることで、初期化やスキャン完了の
  処理が何を呼ぼうと、導出元のフラグ（ホバー/設定画面/ユーザー一時停止）が
  変わらない限り再生は始まらないことを構造的に保証する。`Slideshow.tsx` は同じ
  `isPlaying` を受け取り、`<video>` の `play()`/`pause()` をそこに連動させる。
- **`get_next_image`/`get_previous_image` の結果を `ImageNavigationResult` で
  区別する**（バックエンド側は§3参照）。フロントは `'No more images'` 等の文字列
  比較をせず `kind` で分岐し、`found`/`emptyPlaylist`/`loadFailed`/
  `rootUnavailable`/`noHistory` それぞれに応じた画面/通知を出す。
- **同時実行ガード＋リクエストID**: `useSlideshow` 内の `inFlightRef`（同時実行を
  防ぐ）と `requestIdRef`（万一ガードをすり抜けても古い応答を破棄する保険）の
  二重の仕組みで、キーリピートやタイマーと手動操作の重なりによる二重カウント・
  応答順逆転を防ぐ。キーボードの `keydown` も `e.repeat` を無視する。
- **タイマーは実表示開始（`<img onLoad>`）を起点に `setTimeout` + 残り時間保持**:
  IPC応答時点を起点にするとトランジション/デコード時間が表示時間から引かれ、
  一時停止→再開で残り時間を捨てて0から再開してしまっていた。プログレスバーは
  60fpsの `setInterval`ポーリングをやめ、CSS transition（`transform: scaleX(...)`）
  に「アンカー%→100%へのtransition時間」の2値だけを渡してブラウザに補間させる
  （`OverlayUI` 側の描画）。
- **表示回数の取り消しAPI（`undo_display_count`）**: バックエンドはファイルの
  存在とキャッシュ変換の成功までしか確認できず、WebViewでの実際のデコード/描画
  失敗（壊れたファイル内容等）までは検知できない。`<img>`/`<video>` の `onError`
  で「既に加算済みの表示回数を取り消してから次へ進む」方式にした（加算そのものを
  表示成功後に遅延させる設計にしなかったのは、既存の `should_count`（履歴なぞり中は
  加算しない等）のロジックと実装済みテストを一切変更せずに済むため）。
  **#65レビューS1**: 初版は渡された `path` を無条件に1減らしており、「前へ」で
  戻った画像（`get_previous_image` は表示回数を加算しない）や履歴なぞり中
  （`should_count=false`）の画像で `onError` が起きると、無関係な過去の正当な
  加算まで誤って減らせてしまう抜け穴があった。`AppState.last_incremented_display`
  に「直近に `increment_display_count` を実際に呼んだパス」を保持し、
  `undo_display_count` はこれと `path` が一致した時だけ1回減らして即座にクリアする
  （同じ `onError` が2回届いても2回目は不一致で無視される）よう修正した。

### (h) 動画の音声と最大再生時間（#68）

- **設定は既存の `app_settings` に乗せる**: `video_audio_enabled`（`'true'|'false'`、既定オフ）と `video_max_duration_sec`（秒。`0`=無制限が既定、選択肢 `0/30/60/120/300`）。`save_setting`/`get_setting` は汎用のキー/値ストアでバックエンドは値を解釈しないため、Rust側の変更・検証は無い。破損値（NaN・負数・選択肢外・小数）は `constants.ts` の `parseVideoAudioEnabled`/`parseVideoMaxDuration`/`normalizeVideoMaxDuration` が既定へ丸める（`clampDisplayInterval` と同じ「唯一の検証経路」。UI・起動シーケンス・`App.tsx` の全てがこれを通す）。選択肢外を「最寄りの値へ丸める」のでなく既定（無制限）へ戻すのは、壊れた値で意図しない短い上限（全件を一瞬で消化する）にならないようにするため。起動時の復元は `startup.ts::runStartupSequence`（`display_interval` の直後）が担い、読み込み失敗でも起動は止めない。
- **上限は壁時計タイマーでなく再生位置（`timeupdate` の `currentTime`）で判定する**: 動画は `useSlideshow` のタイマーの対象外（自走）で、`Slideshow.tsx` が `onEnded` で `onAdvance` を呼ぶ。上限も同じ側に置き、`onTimeUpdate` で `currentTime >= videoMaxDurationSec` を見る。一時停止・バッファリング中は再生位置が進まないので、タイマーの張り忘れ・取り消し漏れ（#65 の「永久停止」「二重進行」）が構造的に起きない。`timeupdate` は約4Hzなので上限には最大250ms程度の誤差が出るが許容する。上限より短い動画は上限に届かず従来どおり `onEnded` で進む。
- **`ended` と上限到達は同じ `finishVideo` を通し、1本につき1回しか進めない（#65 の二重進行を再導入しない）**: 自分（その `<video>`）の `mediaKey` が最新でなければ何もしない（退場中の古い要素の弾き。#65 S8）＋ `finishedKeyRef`（処理済みの `mediaKey`）で二重発火を弾く（上限到達後に `timeupdate` が続けて来る・`ended` が遅れて来る等）。上限到達時は `pause()` してから進める（フェード中に最終フレームで止まり、音声も残さない）。一時停止中に到達/終了した場合は `pendingEndedRef` に予約し、再開時に `onAdvance`。**上限で止めた動画を再開しても素の `play()` はしない**（上限を超えて再生が続き二度と進まなくなるため、`finishedKeyRef` が現在の動画と一致する再開は「次へ」として扱う。`useSlideshow` の `inFlightRef` が重複呼び出しを弾く）。`finishedKeyRef` と `pendingEndedRef` は `mediaKey` が変わるたびにリセットする。
- **既知の限界（今回の回帰ではない既存設計）**: 動画は `useSlideshow` のタイマー対象外のため、`finishVideo` が `pause()` → `onAdvance` した後に `onAdvance` が `inFlightRef` ガードで無視されると、最終フレームで止まる（`ended` 側にも同じ性質がある）。
- **音声オンは `muted={!videoAudioEnabled}`。自動再生を拒否されたらその動画だけミュートへ落として再生を続ける**: `autoPlay` 属性の拒否は結果（Promise）を返さず観測できないため、`onLoadedData` で（再生中のはずなのに `paused` なら）明示的に `play()` して拒否を観測し、再開経路も同じ `startPlayback` を通す。`NotAllowedError` の時だけ `muted=true` にして `play()` し直す（`AbortError`＝読込中の差し替え等の別理由でミュートへ落とすと、音声オンなのに無音になるだけなので対象外）。拒否が返るまでに次のメディアへ移った・一時停止された場合は再生し直さない。フォールバックは要素単位で、設定自体は変えない（次の動画はまた音声付きで試みる）。設定画面での切り替えは、現在の動画の `muted` に即時反映される。
- **退場中の古い動画は必ずミュート+一時停止する**: `AnimatePresence mode="wait"` の退場（500ms）の間、`videoRef` はまだ古い要素を指したままで、音声オンだとフェード中に前の動画の音が次のメディアと重なる。`mediaKey` が変わった時点の effect で、`data-media-key` が最新と一致しない（＝退場中の）要素を `muted=true` + `pause()` する。新しい要素（一致する）は対象外。
- **テスト**: `Slideshow.test.tsx`（上限到達で1回だけ進む・二重進行しない・短い動画は `onEnded` で1回・一時停止中は進まず再開で1回・音声オン/オフの `muted` 反映・退場中要素のミュート・自動再生拒否のフォールバック各種）、`constants.test.ts`（検証関数の境界値）、`startup.test.ts`（復元）、`VideoSection.test.tsx`（保存・復元・破損値・a11y）、`messages.test.ts`（ja/en キー一致は自動）。実ブラウザ e2e は `vidset`/`vidcap`/`vidend`/`vidblock`（`e2e/README.md`）。

### (g) 表示言語（`auto`）はOSロケールを優先して解決する（#80/#82）

`app_settings.language`（`'ja'|'en'|'auto'`）が`auto`の時、実際に表示する言語
（`'ja'|'en'`）を決めるロジック。フロントは `src/lib/i18n/store.ts` の
`initLocale()`/`resolveLocale()` が管理する。

- **OSロケールを`navigator.language`より優先する**: macOSのWKWebViewは
  `CFBundleLocalizations`（Info.plist）にアプリの対応言語として明示していない
  ロケールだと、`navigator.language`が実際のOS設定に関わらず`en-US`固定になる
  既知の制約がある。これを避けるため、バックエンドの`get_os_locale`コマンド
  （`src-tauri/src/commands/settings.rs`、`sys-locale`クレート）でOS本来の
  ロケールを取得し、取得できた場合はこちらを使う。取得できない（`None`/
  例外）場合だけ`navigator.language`にフォールバックする。
- **`tauri-plugin-os`は使わない**: プラグイン全体を追加するとcapability許可
  （`os:allow-locale`）が増える。素の`#[tauri::command]`（capability不要）+
  `sys-locale`クレートで最小限に実装した。
- **`initLocale`は保存値にかかわらず毎回`get_os_locale`を呼ぶ**
  （`cachedOsLocale`に結果をキャッシュする）。以前は保存値が`auto`の時だけ
  呼んでいたが、`ja`/`en`を明示保存している間はキャッシュが空のままになり、
  後から設定画面で「自動」に切り替えた直後は`navigator.language`ベースの
  解決にしかならず、OSロケールへ切り替えるにはアプリの再起動が要った
  （#82レビュー2巡目 should2）。常に取得しておくことで、`auto`への切替直後
  から再起動なしでOSロケールが反映される。
- **`initLocale`は`getSetting`/`getOsLocale`のどちらが失敗（reject）しても
  内部で吸収し必ずresolveする**（#82レビュー must）。`App.tsx`はこの
  `.then()`の中で起動シーケンス本体を走らせているため、ここでrejectすると
  起動画面のまま永久に止まる。
- **ロケールタグの正規化**（`normalizeLocaleTag`、`/^ja([-_.@]|$)/i`）:
  `navigator.language`（`ja-JP`のような`-`区切り）と`get_os_locale`の返り値
  （`ja_JP.UTF-8`のような`_`区切り、`ja@euro`のようなmodifier付き、`C`のような
  ロケール未設定を表す値等）の両方を同じ基準で判定する。「`ja`で始まる」の
  単純な前方一致だと、ジャマイカ・クレオール英語のISO 639-3コード`jam`まで
  日本語と誤判定するため、直後が区切り文字か文字列終端であることも要求する。

### (i) 失敗を「空」や成功に見せない（#115）

IPC（`invoke`）の失敗は、利用者に見える形で伝える。取得は `useAsyncLoad`（`loading | error | ready`）で受け、reject は「読み込みに失敗しました」＋再試行（`LoadError`）にする。「〜はありません」の空状態は `ready` かつ 0 件のときだけ。保存は `useRollbackSave` で、直列化して書き込み、失敗したら最後に保存できた値へ巻き戻してセクション内に1つだけ対象名つきの通知（`InlineError`）を出す。セクションが既にアンマウントされている場合は `lib/failureNotice.ts` 経由で App の上部トーストにも出す（巻き戻しだけが説明なしに起きない）。起動シーケンス（`lib/startup.ts`）の失敗は `onStartupFailure` で App に伝え、前回フォルダの取得失敗・想定外の初期化失敗は「ようこそ」にせず再試行できる案内画面、設定の取得失敗は既定値で続行して上部トーストで知らせる。ピック失敗の原因は Rust の `pick::pick_io_error_code`（書き込み側: `pickPermissionDenied` / `pickDiskFull` / `pickDestinationMissing`（`create_dir_all` の AlreadyExists/NotADirectory も含む。純粋関数 `create_dir_error_code`）、その他は `pickCopyFailed`）と `pick::pick_source_error_code`（読み取り側: `pickSourceUnreadable` / `imageFileNotFound`）で返し、`resolvePickErrorMessage` が原因別の文言にする。保存済みの値(巻き戻し先)は、設定の取得に成功していればその値、取得に失敗したまま(`loadFailed`、既定値を表示している状態)で最初の保存が失敗したときは**既定値**。取得が返る前にユーザーが保存を始めていた場合、古い DB 読み取りで巻き戻し先を上書きしない(取得の世代管理 `beginLoad`/`markLoaded`)。分類は `std::io::ErrorKind` のみで行い、OS の生エラーコードは見ない（OS ごとに意味が違うため。std が ENOSPC や Windows の ERROR_DISK_FULL を `StorageFull` に写す）。

**Windows での `tests/*.rs`（`tauri::test::mock_app` 系）起動失敗への対処**（PR#83レビュー由来）— `tauri_build::build()` が埋め込むアプリ本体用の Windows マニフェスト（Common Controls v6 宣言、tao/wry が要求）は `embed-resource` の `compile()` 経由で `-bins` 相当にしか届かず、`cargo test` が作る `tests/` 配下の integration test バイナリには適用されない（tauri-apps/tauri#13419、未修正）。マニフェストが無いと Windows は comctl32 の旧実装（v5.82、tao/wry が使う v6 専用シンボル非対応）を読み込み、プロセスがロード時点で `STATUS_ENTRYPOINT_NOT_FOUND`（0xc0000139）で落ちて1テストも走らない。`src-tauri/build.rs` で同内容のマニフェスト（`src-tauri/windows-test-manifest.xml`）を `cargo:rustc-link-arg-tests` により `tests/` 配下のバイナリにのみ追加リンクして解消している（`-tests` サフィックスのためアプリ本体の `-bins` 側とは独立で二重埋め込みにならない）。`src/` 内 `#[cfg(test)]`（lib unit test バイナリ）は `AppHandle` の runtime が `Wry` 固定で `MockRuntime` を受け付けないため `mock_app` を使っておらず、この対処だけで足りる。
